## Objective

Change `Story.content` in `types/narrative.ts` from `string` to `string | PortableTextBlock[]`. This corrects a type mismatch between the Sanity schema (which defines `content` as a PortableText block array) and the TypeScript interface (which incorrectly types it as a plain string). The change is backward-compatible — static data (`lib/data/stories.ts`) stores plain strings, which remain valid members of the union.

## Implementation Guidance

### Why @portabletext/types and not @portabletext/react

`@portabletext/types` is a lightweight types-only package (`PortableTextBlock` and related interfaces). `@portabletext/react` is the renderer — it depends on React and is heavier. C4 only needs the types; C5 adds the renderer.

### Import placement in narrative.ts

Place the import at the top of the file, before the interface definitions:
```typescript
import type { PortableTextBlock } from '@portabletext/types';
```

### Union type note

The union `string | PortableTextBlock[]` means:
- A plain string (like `"# Title\n\nBody text..."`) is valid
- An array of PortableText blocks is valid
- TypeScript will require a type guard before calling string-only methods (`.split()`, `.trim()`, etc.) directly on `story.content`

The GROQ query in `lib/sanity/queries.ts` line 154 (`content,`) returns the raw content field from Sanity, which will be a `PortableTextBlock[]`. Static data files use strings. Both are now correctly typed.

### After C2 has run

`types/narrative.ts` will already have been modified by C2 (the `ImpactMetric` interface replaced with a type alias, and `Story.impactMetrics` updated to `ImpactPoint[]`). Read the file as it exists when you start C4 — do not revert C2's changes.

### Edge Cases
