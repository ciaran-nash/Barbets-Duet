## Implementation Guidance

### Pattern to follow — type alias approach

The type alias technique preserves all existing component imports:

```typescript
// OLD (delete this):
export interface ImpactStat {
  label: string;
  value: string;
  description: string;
  trend?: 'up' | 'down';
}

// NEW (replace with these two lines):
import type { ImpactPoint } from '@/types/shared';
export type ImpactStat = ImpactPoint;
```

Because `ImpactPoint` is a superset of `ImpactStat`, this alias is structurally compatible — any code that reads `stat.description` will still work because `ImpactPoint` has `description?`. The only difference is that `description` is now optional rather than required. Existing static data (`lib/data/learning-sites.ts`) provides `description` on all `ImpactStat` entries, so this is safe.

### Import path convention

The project uses `@/` path aliases (configured in `tsconfig.json`). Always use:
```typescript
import type { ImpactPoint } from '@/types/shared';
```
not relative paths.

### Backward compatibility note for ImpactStat

`ImpactStat.description` was previously required (`description: string`). In `ImpactPoint`, it is optional (`description?: string`). This is a widening, not a narrowing — existing code that reads `.description` will still compile, but TypeScript will now require null-checks if writing new code that does so. This is the correct direction.

### Edge Cases

- Do not add `@deprecated` JSDoc annotations — the deprecated aliases are intentionally kept clean for now (a future cleanup PRD will remove them).
- Do not change the import style in the three type files from named imports to default imports.
- Do not change `tsconfig.json`.
